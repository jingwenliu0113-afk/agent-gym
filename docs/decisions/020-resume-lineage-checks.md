# 020 — 續跑的血緣檢查與可重複的 --resume-from（第十輪審查後；在任何 LLM 結果之前）

日期：2026-10-09　狀態：採用（補足 decision 019 §1 / §3；不改主要 metric、資料切分、模型、SweepPlan 或 criterion）

## 背景

第十輪對抗式審查（decision 019 的實作）確認兩個缺陷：

1. **`--resume-from` 重複給時只保留最後一個值**（019 只修了 `--baseline-run`）。依給的順序不同，結果有兩種：
   - 被拒絕，但錯誤訊息誤導；
   - 少了一個目錄卻照常執行，該目錄完成的 source 被重新 sweep、再付一次費。
2. **019 §3 只能發現漏給「較早」的目錄**。它只檢查給定目錄略過的 source。如果漏給的是「較晚」的目錄，不會被發現。最常見的情況是：
   續跑被 Ctrl-C 中斷後，從 shell 歷史重下同一個指令，只改 `--run-name`。結果是：
   - 那個目錄已完成的 source 會再付一次費；
   - 所有目錄無法一起分析（017 §5.1）；
   - 只分析其中一部分目錄時，看起來完整，卻漏掉成本。

同一輪判定「不是缺陷」、但成本很低而一併處理的有兩項：
- rollout 0 的同時間檢查結果依傳入順序而定。source 在任何順序下都相同，只有「不是最早的那兩條時間相同」時，某些順序會多一個 ValueError。
- 目錄已存在時，錯誤訊息沒有提示要用 `--resume-from` 續跑。

## 決策

1. `--resume-from` 與 `--baseline-run` 一樣可以重複給，所有值都會保留。
2. `run.json` 增加兩個欄位，sweep 格式升為 `agent-gym/sweep-run/v5`：
   - `run_id`：開始時產生的隨機 32 位小寫 hex；
   - `resumed_from`：這次 `--resume-from` 各目錄的 run_id，排序後列出。
3. **續跑前的後代檢查**。範圍是兩處，都不遞迴：`--resume-from` 各目錄的上層目錄，以及新目錄的上層目錄。在其中找出同時符合
   以下條件的目錄：
   - `run.json` 的 resumed_from 含有任一給定目錄的 run_id；
   - 有 manifest；
   - 沒有被傳入。

   找到時拒絕執行：不建立目錄、不發出任何 call，列出這些目錄並要求一起傳入。
   - 比對只用 run_id 的血緣，不依目錄名稱或內容猜測，所以無關的目錄不會被算進來；檢查只用來拒絕，不會自動加入任何目錄
     （019 放棄的「掃描 runs/ 自動加入」仍然不採用）。
   - 沒有 manifest 的後代（第一次嘗試前就中斷），沒有可分析的內容，不需要傳入（018 §4）。
   - 019 §3 要求每次續跑都列出所有先前目錄，所以每個後代的 resumed_from 都含所有祖先的 run_id。因此只比對一層就涵蓋整條鏈。
   - 限制：放在其他位置的後代目錄偵測不到（記在 NEXT 的已知限制）。
4. analyze_sweep 逐欄驗證 run_id 與 resumed_from。同一個 run_id 出現在兩個目錄（例如複製的目錄）→ ValueError。
5. rollout 0 的同時間檢查只看最早的時間：最早時間有兩條以上 → ValueError；較晚的同時間紀錄不影響。結果與傳入順序無關（019 §1 的釐清）。
6. 目標目錄已存在且不是空的：CLI 在任何 call 之前報錯，並提示用新的 `--run-name` 加 `--resume-from` 續跑。

## 為什麼

- 付費 sweep 中斷後，最可能的操作就是「重下上一個指令」。019 §3 的承諾是「同一個 source 不能因為漏給一個目錄就再付一次費」，
  必須對較早與較晚的目錄都成立。
- 只有新目錄知道自己是從哪些目錄續跑的，所以血緣記錄在新目錄的 run.json，不需要回頭修改已完成的目錄。

## 放棄的替代方案

- 在舊目錄寫入「已被續跑」的標記：會修改已完成的 run 目錄。
- 沒有 `--resume-from` 的新 sweep 也檢查 runs/ 中設定相同的目錄：無法分辨「刻意重新開始」與「忘了續跑」。新 sweep 不是續跑，
  所以只在錯誤訊息中提示。

## 對實驗的影響

- 不影響任何估計方法、判定規則或主要 metric。
- 目前還沒有任何真實的 sweep 資料，格式升版不影響既有結果。
